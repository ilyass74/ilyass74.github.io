From a network event to an incident you can investigate.

Preserve the event before interpreting it

Python producers collect public RIPE Atlas measurements or inject explicitly controlled scenarios. A separate OpenTelemetry path ingests laboratory service signals. Kafka transports the messages; Bronze stores their original JSON alongside topic, partition, offset and ingestion time. Those positions allow the investigation to distinguish a delivery from the business event it contains. Iceberg stores the local tables and their snapshots; the warehouse is on local disk, not MinIO.

Make retries and late data explainable

Silver parses the event contract, records invalid inputs in a rejection table and deduplicates valid records by event_id. Within each micro-batch it removes repeated IDs; an insert-only Iceberg MERGE protects against IDs already committed by an earlier batch. Rejections use Kafka position as their key. The base jobs use availableNow and terminate after consuming available input. A separate persistent scenario worker reuses the verified processing plans for the measured low-latency path. These are different execution modes, not an always-on claim about every job.

Keep service statistics faithful to the observations

OpenTelemetry Gold reads pinned, verified Silver snapshots. It separates SERVER spans from CLIENT and INTERNAL spans, computes latency percentiles from individual server spans, and displays error rate with outcome coverage. Missing outcomes remain unknown. Cumulative counters require compatible baselines; resets break the interval. Histogram buckets are not converted into a fabricated p95. Late records are retained, and windows without observations do not establish either health or downtime.

Turn anomalous windows into an investigation

Network Gold produces analysis windows; scenario detection groups abnormalities into incidents and builds a timeline with evidence references. The first-signal module examines individual measurements, rather than treating the declared incident start as the first observation. Replay limits charts to the selected historical point. Service, controlled incident and public-network views keep their provenance separate: coincident signals do not prove a shared cause.

A read-only assistant with a verifiable boundary

The assistant selects from authorized read functions and admitted fact IDs. The server renders numbers, periods and warnings from the evidence; arbitrary model prose is not accepted as a factual diagnosis. Queries use immutable SQLite service exports, while network and incident views use verified JSON. Export identity and source references accompany answers. The assistant does not execute generated code, change services or claim that recorded laboratory telemetry describes a live infrastructure.

Validate the failure boundary, not only the happy path

The recorded Windows acceptance includes 1,100 Bronze messages resolving to 1,000 unique Silver IDs with controlled duplication and 100 late events. A specific Spark interruption after the Silver write but before checkpoint commit replayed the batch and retained 200 Bronze positions and 200 Silver IDs. One prepared-worker run took 48.5547345 seconds from injection to rendered evidence, against a 60-second target. This is one warm-service measurement, not a percentile or production SLA. The later English presentation update records 75 fixture/model-double Python tests; raw native acceptance exports are not published in the repository.

Scope & limitations

  • Local delivery; cloud deployment is deferred.
  • The latency result is one controlled run with Spark already ready.
  • An anomaly is not proof of root cause, user impact or present service status.
  • Raw Windows acceptance reports are private; the public repository contains summaries and fingerprints.
